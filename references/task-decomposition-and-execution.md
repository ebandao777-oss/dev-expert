# 任务拆解与执行 -- 复杂任务拆解与Wave执行

## 输入要求

1. **需求或spec**（必填）：需要实现的功能描述或已有spec
2. **现有代码**（可选）：相关代码片段或文件列表
3. **约束条件**（可选）：时间、性能、依赖限制

## 执行流程

### 第一步：需求分析

- 理解核心目标和边界
- 如需求属于做网站/建站/企业官网/CMS网站/营销页/网站上线，先调用 `网站项目总控` 确认站点规划、SEO、部署、验收和运维阶段，再进入任务拆解
- 如需求属于 API服务/后端服务/后台模块/CLI工具/数据脚本/自动化任务/插件项目，先调用 `软件项目总控` 确认边界、架构、数据/API、发布、回滚和交付阶段，再进入任务拆解
- 识别隐含依赖（如"用户系统"依赖"数据库表已存在"）
- 识别风险点（复杂算法、第三方集成、性能瓶颈）
- 识别安全触发面：外部输入、权限、数据库、文件上传、API、后台操作、长任务、第三方回调

### 第二步：原子任务拆解

将复杂需求拆分为2-7个原子任务（每Wave 2-5个）。每个任务必须满足：

- **单一职责**：只解决一个明确问题
- **可独立完成**：一个context window内可完成
- **可验证**：有明确的完成标准
- **可回滚**：失败时不影响其他任务
- **安全可验收**：涉及输入/权限/数据/文件/API/后台操作的任务必须包含安全检查项

**任务结构（XML格式）**：

```xml
<task type="auto|human-verify|decision">
  <name>[任务名称]</name>
  <files>[涉及文件列表]</files>
  <action>
    [具体执行步骤]
  </action>
  <verify>
    [验证方法：测试命令/检查清单/人工确认]
  </verify>
  <security>
    [安全验证：SQL注入/XSS/CSRF/权限绕过/文件上传/反序列化/敏感信息泄露；不涉及则写"不涉及，原因：..."]
  </security>
  <done>
    [完成标准：什么状态算完成]
  </done>
</task>
```

### 第三步：Wave分组

按依赖关系将任务分组：

```
Wave 1（并行，无依赖）
├── Task 1.1: [任务A]
└── Task 1.2: [任务B]

Wave 2（依赖Wave 1）
├── Task 2.1: [任务C，依赖1.1]
└── Task 2.2: [任务D，依赖1.2]

Wave 3（依赖Wave 2）
└── Task 3.1: [任务E，依赖2.1和2.2]
```

**分组原则**：

- 无依赖的任务 → 同一Wave，可并行
- 有依赖的任务 → 后续Wave，必须串行
- 可能文件冲突的任务 → 同一Wave内串行或合并为一个任务
- 涉及安全触发面的Wave → 必须安排安全验证任务或在每个相关任务的 `<security>` 中给出验证方法

### 第四步：上下文隔离

执行单个任务时，只加载必要上下文：

```
任务上下文 = {
  spec: [相关requirement和scenario],
  design: [相关技术决策],
  files: [该任务需要读写的文件],
  decisions: [影响该任务的历史决策],
  previous_summary: [前置Wave的任务summary]
}
```

**禁止加载**：

- 无关模块的代码
- 已完成的无关任务细节
- 未决但无关的讨论

### 第五步：执行与验证闭环

每个任务执行后：

1. **执行**：按action完成代码修改
2. **自测**：运行verify中的验证方法
3. **记录summary**：

   ```
   ## Task Summary: [任务名]

   **完成状态**: [完成/部分完成/失败]
   **修改文件**: [文件列表]
   **关键决策**: [执行中做出的决策]
   **偏差说明**: [与plan的差异及原因]
   **遗留问题**: [未解决的问题]
   ```

4. **验证通过**：标记done，进入下一任务
5. **验证失败**：修复或回滚，重新执行

### 第六步：记录到项目记忆

所有Wave执行完毕后，将任务执行结果和关键决策沉淀到项目记忆（参见 `project-memory-management.md`）：
- 汇总各任务的 summary，生成整体执行报告（Session Summary 模式）
- 记录执行中的关键决策和偏差（Decision Record 模式）：如任务拆分调整、依赖关系变更
- 记录新发现的项目约束和规范（Convention Capture 模式）：如文件组织约定、模块边界规则

## 质量标准

- 每个任务必须可在单个context window完成（建议不超过200行代码变更）
- 每个任务必须有明确的verify方法，不能是"看起来对就行"
- Wave分组必须明确标注依赖关系
- 涉及外部输入、权限、数据库、文件上传、API、后台操作、长任务、第三方回调的任务，必须写明安全验证方法
- 安全验证不得只写"已检查"，必须指向具体风险：SQL注入、XSS、CSRF、权限绕过、文件上传、反序列化、敏感信息泄露
- 任务summary必须记录偏差，不能假装一切按计划进行
- 失败任务必须说明原因，不能默默跳过
- 优先"垂直切片"（端到端功能）而非"水平分层"（全部模型→全部API）

## 失败回退机制

| 步骤 | 失败条件 | 回退目标 | 最大重试 | 不可恢复时升级路径 |
|------|---------|---------|---------|------------------|
| 第一步：需求分析 | 需求边界不清，隐含依赖未识别 | 基于已知信息拆解，标注"依赖待确认" | 1 | 输出需求澄清清单，等待用户补充 |
| 第二步：原子任务拆解 | 任务数量超出单次context window容量 | 按模块/资源域拆分为多个Wave集合 | 1 | 建议拆分为多个独立Spec驱动开发会话 |
| 第三步：Wave分组 | 任务间存在循环依赖 | 识别循环并合并为单任务，或引入中间状态 | 2 | 输出依赖图，建议架构层面解耦 |
| 第四步：上下文隔离 | 任务上下文跨Wave污染 | 强制重置context，仅加载previous_summary | 1 | 标注"上下文隔离失败"，建议人工接管 |
| 第五步：执行与验证闭环 | 验证连续失败3次 | 暂停执行，输出差异分析 | 0 | 标记任务为"阻塞"，输出阻塞清单移交人工 |
| 第六步：记录到项目记忆 | 项目记忆系统不可用 | 输出执行报告和决策到本地文件 | 1 | 标注"执行结果未沉淀"，提示用户手动保存 |

## 关联Skill

- **网站项目总控** — 建站类需求拆解前先定义完整生命周期阶段和上线交付清单
- **软件项目总控** — 非网站类完整项目拆解前先定义边界、架构、验证、发布和交付清单
- **Spec驱动开发** — 拆解前用 `Spec驱动开发` 确保需求已对齐
- **API设计** — API/服务类任务拆解前先定义接口契约、认证、错误码和分页
- **前端设计** — 页面/后台交互任务拆解前先定义组件、状态、响应式和浏览器验证
- **CMS二次开发** — CMS/PHP二开任务拆解前先确认CMS访问层、插件入口和兼容性
- **MySQL数据库** — 数据库/SQL任务拆解前先定义表结构、索引、事务、迁移和回滚
- **代码生成** — 每个task可用 `代码生成` 实现具体代码
- **代码审查** — 每个task完成后用 `代码审查` 检查质量
- **测试用例生成** — 每个Wave完成后补充正常、异常、边界、回归、安全、性能和长任务测试
- **文档生成** — 交付前生成README、API文档、部署说明和使用说明
- **项目记忆管理** — 将task summary和决策记录到项目记忆
