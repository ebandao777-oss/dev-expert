# 项目记忆管理 -- 跨会话项目记忆沉淀

## 输入要求

1. **记录类型**（必填）：session总结 / 决策记录 / 规范沉淀 / 记忆恢复
2. **内容详情**（必填）：具体要记录的信息
3. **项目标识**（可选）：项目名称或标识符

## 执行流程

### 第一步：会话结束记录（Session Summary）

会话结束时生成结构化summary：

```markdown
## Session Summary

**日期**: [YYYY-MM-DD]
**会话目标**: [本次会话原计划完成什么]

### 已完成

- [任务1]: [简要说明] → [相关文件]
- [任务2]: [简要说明] → [相关文件]

### 关键决策

- **决策**: [决策内容]
  - **上下文**: [为什么做这个决策]
  - **影响**: [影响哪些后续工作]

### 遗留问题 / Blockers

- [问题1]: [描述] → [下一步行动]

### 下一步计划

1. [下一步任务]
2. [下一步任务]

### 规范更新

- [新发现的项目规范]
```

### 第二步：决策记录（Decision Record）

重要技术决策时记录：

```markdown
## Decision Record: [决策名称]

**日期**: [YYYY-MM-DD]
**问题**: [需要解决什么问题]

### 选项分析

| 选项    | 优势 | 劣势 | 复杂度   |
| ------- | ---- | ---- | -------- |
| [选项A] | ...  | ...  | 低/中/高 |
| [选项B] | ...  | ...  | 低/中/高 |

### 决策

**选择**: [最终选项]
**理由**: [为什么选这个]
**Trade-offs**: [接受了什么代价]

### 影响范围

- [影响的模块/文件]
- [需要同步更新的文档]

### 撤销条件

[什么情况下可以重新考虑这个决策]
```

### 第三步：规范沉淀（Convention Capture）

发现项目特定规范时记录：

```markdown
## Project Convention: [规范名称]

**类型**: [编码规范/命名规范/架构约束/工具配置]
**适用范围**: [哪些模块/文件适用]

### 规范内容

[具体规则]

### 示例

**正确**:
`[代码示例]`

**错误**:
`[代码示例]`

### 发现来源

[哪次会话/哪个任务中发现]
```

### 第四步：新会话记忆恢复（Progressive Disclosure）

新会话开始时，按三层加载记忆：

**Layer 1: Metadata（~50 tokens）**

```
项目: [名称]
当前阶段: [阶段]
活跃任务: [任务名]
上次会话: [日期]
```

**Layer 2: Body（~200 tokens）**

```
## 上次Session Summary
[最近一次的summary核心内容]

## 活跃决策
- [与当前任务相关的决策]
```

**Layer 3: References（按需加载，~500 tokens each）**

```
## 相关决策记录
[与当前任务相关的完整决策记录]

## 相关规范
[与当前任务相关的项目规范]
```

**加载策略**：

1. 始终加载Layer 1
2. 如果当前任务与上次会话连续，加载Layer 2
3. 如果涉及历史决策或规范，按需加载Layer 3
4. 总token预算控制在1000以内，避免context rot

### 分层记忆金字塔

记忆沉淀和恢复必须按稳定性分层，避免把短期上下文误写入长期规范，也避免把用户级偏好塞进单次任务摘要。

| 层级              | 内容范围                                           | 生命周期           | 写入条件                           | 恢复优先级                      |
| ----------------- | -------------------------------------------------- | ------------------ | ---------------------------------- | ------------------------------- |
| L1 对话级临时记忆 | 当前轮目标、正在编辑的文件、刚产生的错误、临时假设 | 当前会话内有效     | 执行中产生，尚未验证或只影响当前轮 | 最高，但会话结束后不长期沉淀    |
| L2 会话摘要       | 已完成任务、已验证结果、未决阻塞、下一步动作       | 跨会话短期有效     | 本轮主线交付完成或发生中断/压缩    | 高，恢复连续任务时优先加载      |
| L3 项目级记忆     | 技术决策、项目约束、编码规范、目录约定、验证方法   | 项目生命周期内有效 | 决策被验证、重复出现或影响后续任务 | 中，只有命中当前项目/模块时加载 |
| L4 用户级偏好     | 用户长期偏好、禁用操作、常用环境、交付格式         | 跨项目长期有效     | 用户明确表达或多次稳定出现         | 按需加载，不能覆盖项目级硬约束  |

分层写入规则：

1. 未验证信息只能留在 L1，不得沉淀为 L3 项目规范。
2. 只影响本轮执行的路径、临时命令、一次性错误不得写入 L4。
3. L4 用户偏好与 L3 项目约束冲突时，优先遵守更具体、更高风险的项目约束，并在摘要中标注冲突。
4. L2 会话摘要必须能恢复任务状态，但不能替代 L3 中已稳定的项目规范。

### 上下文预算阈值

长任务或跨会话任务必须显式控制上下文窗口，避免把无关历史、资料型 reference 或过期决策带入当前推理。

| 阈值        | 触发条件                                                 | 动作                                                                               |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 60%         | 对话历史、文件片段和参考资料合计超过可用上下文预算的 60% | 生成结构化摘要，保留当前目标、关键决策、改动范围、阻塞项和验证证据                 |
| 80%         | 上下文继续增长且接近窗口上限                             | 只保留当前任务必需文件、直接引用、仍生效决策和未解决阻塞；暂停加载资料型 reference |
| 1000 tokens | 项目记忆恢复阶段的默认加载上限                           | 优先加载 Layer 1 + Layer 2；Layer 3 仅在当前任务命中时加载                         |

上下文压缩、会话交接或中断恢复时，必须使用以下最小字段，禁止只写泛泛总结：

### Typed Memory 类型映射

写入记忆前必须先判定记忆类型，再映射到 L1-L4 分层，避免把用户偏好、项目规范、一次性反馈和参考资料混写。

| 类型      | 内容范围                                         | 推荐层级      | 写入条件                                 | 过期/撤销条件                          |
| --------- | ------------------------------------------------ | ------------- | ---------------------------------------- | -------------------------------------- |
| user      | 用户长期偏好、禁用操作、常用环境、交付格式偏好   | L4 用户级偏好 | 用户明确表达，或跨任务稳定重复出现       | 用户撤销、偏好与当前项目硬约束冲突     |
| feedback  | 用户对本轮输出、修改方式、节奏、格式的即时反馈   | L1 或 L2      | 当前任务需要立即调整，或会影响下一轮继续 | 当前主线结束，且未重复出现             |
| project   | 项目目录、技术决策、编码规范、验证方法、风险边界 | L3 项目级记忆 | 已验证、被用户确认，或影响后续同项目任务 | 新证据推翻、项目约束变更、用户要求废弃 |
| reference | 可复用资料、模板、外部文档摘要、历史方案索引     | L2 或 L3      | 被当前任务命中，且能减少重复检索         | 资料过期、链接失效、与最新项目决策冲突 |

类型映射规则：

1. 同一条记忆只能有一个主类型；如同时命中多类，按 `project > user > feedback > reference` 选择主类型，并在备注中标注关联类型。
2. `feedback` 不得直接沉淀为 `user`，除非用户明确要求记住或跨任务重复稳定出现。
3. `reference` 只能作为辅助上下文，不能替代当前任务的验证证据。
4. `project` 与 `user` 冲突时，优先遵守更具体、更高风险、更接近当前交付的项目约束。

### 记忆创建策略

记忆创建分为强制创建和选择性创建。强制创建用于保证连续性和安全边界；选择性创建用于沉淀稳定经验，避免记忆膨胀。

| 策略       | 触发条件                                                                       | 动作                                                   | 禁止行为                                 |
| ---------- | ------------------------------------------------------------------------------ | ------------------------------------------------------ | ---------------------------------------- |
| 强制创建   | 用户明确说“记住”、项目硬约束被确认、验证方式影响后续交付、阻塞项跨轮延续       | 立即写入对应类型和层级，并记录来源、适用范围、撤销条件 | 不得拖到会话结束后凭记忆补写             |
| 选择性创建 | 重复出现的用户反馈、可复用但非关键的资料、一次任务中发现的局部经验             | 先留在 L1/L2，经过验证或重复后再沉淀到 L3/L4           | 不得把一次性偏好或临时路径升级为长期规则 |
| 禁止创建   | 未验证猜测、敏感无关信息、纯过程噪声、失败的临时尝试、与当前任务无关的个人细节 | 不写入长期记忆；必要时只在当前轮作为 L1 临时上下文     | 不得为了“完整记录”污染项目或用户记忆     |

创建检查：

1. 写入前必须回答：这条记忆属于什么类型、服务哪条主线、何时失效、谁可以撤销。
2. 无法回答失效条件时，只能作为 L1 临时记忆。
3. 写入 L3/L4 前必须确认它会影响后续任务，否则保持在 L2 摘要中。
4. 记忆创建不得替代交付验证；没有验证证据的规则必须标注未验证或待确认。

### CRUL 记忆生命周期

项目记忆必须按 `Create / Retrieve / Use / Learn` 闭环处理，避免只写不取、只取不更新或把旧记忆长期污染当前任务。

| 阶段          | 触发条件                                               | 必须动作                                       | 禁止行为                                     |
| ------------- | ------------------------------------------------------ | ---------------------------------------------- | -------------------------------------------- |
| Create 创建   | 用户明确要求记住、规则被多次验证、项目约束影响后续任务 | 写入对应记忆层级，记录来源、适用范围和撤销条件 | 不得把未验证猜测写成项目规范                 |
| Retrieve 检索 | 用户要求继续、任务命中项目/模块/路径/历史决策          | 按 L1-L4 和延迟加载协议取最小必要记忆          | 不得一次性加载无关历史或全量 references      |
| Use 应用      | 记忆与当前任务直接相关且仍有效                         | 用记忆影响方案、编辑边界和验证路径             | 不得显式暴露无关个人记忆或把记忆当作唯一证据 |
| Learn 更新    | 验证结果推翻旧决策、用户修正规则、任务完成产生稳定约束 | 更新、降级或标注旧记忆过期，并保留冲突原因     | 不得保留互相冲突的有效规则                   |

### 静默应用规则

记忆用于提升连续性和减少重复确认，但默认静默应用。除非用户询问“你记得什么”、要求解释依据，或当前决策依赖一条可能有争议的历史规则，否则不得在回答中主动强调“根据记忆”。

静默应用边界：

1. 可静默使用：用户长期偏好、项目固定路径、已验证技术约束、上轮已确认的下一步。
2. 必须显式说明：记忆与当前请求存在冲突、记忆可能过期、会影响文件修改范围或交付判断。
3. 禁止使用：与当前任务无关的个人信息、敏感背景、未验证历史猜测。

### 敏感记忆隔离

敏感记忆只能在用户主动提起或任务直接相关时使用。健康、财务、身份、家庭变故、私密关系、账号凭据、生产密钥、法律风险等信息不得在无关上下文中主动引用。

隔离规则：

1. 敏感信息不得写入普通项目规范或通用摘要。
2. 交付说明不得复述与当前任务无关的敏感记忆。
3. 当敏感记忆与项目交付冲突时，只描述任务风险和所需输入，不展开敏感细节。
4. 发现误写敏感记忆时，立即标注为污染项，并请求用户确认删除或降级处理。

### 记忆治理失败模式

记忆治理失败不是单次摘要错误，而是会持续影响后续任务的系统性偏差。出现以下模式时，必须优先收敛记忆范围，再继续执行主线任务。

| 失败模式   | 典型信号                                                | 风险                                             | 处理规则                                                             |
| ---------- | ------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| 记忆膨胀   | L2/L3/L4 持续增加低价值细节，恢复时需要加载大量无关记录 | 上下文窗口被历史噪声占满，当前任务推理空间被挤压 | 执行记忆瘦身，只保留仍有效的目标、决策、约束、验证方法和阻塞项       |
| 记忆冲突   | 同一项目存在多个互斥规范、路径、验证口径或用户偏好      | 后续执行在旧规则和新证据之间摇摆，导致错误交付   | 按时间、证据强度、风险等级和用户确认顺序选择有效规则，旧规则标注过期 |
| 透明度不足 | 记忆影响了修改范围、风险判断或交付结论，但未说明依据    | 用户无法复核为什么采用某个边界或默认假设         | 对影响交付边界的记忆显式说明来源类别、适用范围和是否仍需确认         |

治理边界：

1. 记忆膨胀处理不得删除仍有效的主线目标、验证证据、撤销条件和阻塞项。
2. 记忆冲突未解决前，不得把任一冲突规则写成稳定项目规范。
3. 透明度不足的修复只说明与当前任务相关的依据，不暴露无关或敏感记忆。
4. 三类失败模式触发后，交付说明必须标注本轮是否发生记忆瘦身、冲突裁决或依据显式化。

```markdown
## Context Summary

### 用户目标

[当前主线目标和可验收交付物]

### 已确认决策

- [仍然生效的技术/流程/范围决策]

### 当前改动范围

- [文件/模块/功能边界]

### 未决问题 / 阻塞

- [阻塞原因] → [需要谁提供什么输入]

### 验证证据 / 下一步

- [已完成的验证命令、结果或手动验收证据]
- [下一步最小可执行动作]
```

### 对话状态连续性

跨轮对话不得每次重新分类或重置任务状态。进入新一轮时，必须先继承仍然有效的目标、决策、阻塞和验证状态，再判断是否需要调整执行模式。

| 状态项       | 必须继承的内容                             | 失效条件                                 |
| ------------ | ------------------------------------------ | ---------------------------------------- |
| 主线目标     | 用户原始需求、当前可验收交付物、完成度口径 | 用户明确改目标或主线已交付               |
| 已确认决策   | 技术方案、文件范围、执行模式、风险边界     | 新证据推翻、用户撤销或项目约束冲突       |
| 当前执行位置 | 已完成步骤、正在处理的文件、下一步最小动作 | 文件不存在、任务被重排或验证失败要求回退 |
| 阻塞状态     | 阻塞原因、已尝试动作、需要谁提供什么输入   | 用户补齐输入或找到替代验证路径           |
| 验证状态     | 已运行命令、结果、失败证据、剩余风险       | 代码再次修改或验证环境变化               |

连续性规则：

1. 新一轮回复前先判断是否延续上一轮主线；延续时不得重新开启无关分析。
2. 用户只说“继续/下一步”时，默认执行上一轮记录的下一步最小动作。
3. 用户新指令与旧主线冲突时，以新指令为准，并在摘要中标注旧主线是否暂停。
4. 验证失败或发现新风险时，必须更新状态，不得沿用旧的“已完成”判断。

### 延迟加载协议

默认只加载入口文件、当前目标文件和直接引用文件。跨模块资料必须由以下信号触发：

1. 用户明确指定目录、文件、模块或历史上下文。
2. 当前文件存在直接引用、路由、include/import、脚本调用或配置依赖。
3. 错误日志、测试失败、构建失败或验证结果指向相关文件。
4. 当前任务需要比对项目规范、历史决策或跨技能协同规则。

未命中触发信号时，不预读全量 references、不批量展开无关模块、不把资料型文档塞入当前上下文。

### 压缩失败模式

上下文压缩不是简单删减文本。出现以下模式时，必须立即回退到结构化摘要或重新加载最小必要上下文：

| 失败模式     | 典型表现                                                   | 处理规则                                         |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------ |
| 过度压缩     | 摘要只剩结论，丢失文件路径、验证证据、阻塞原因或下一步动作 | 重新生成摘要，补齐 Context Summary 五字段        |
| 加载太晚     | 执行到一半才发现缺少项目规范、历史决策或直接引用文件       | 暂停执行，按延迟加载协议补读最小必要文件，再继续 |
| 记忆层级混乱 | 临时猜测被写成项目规范，用户偏好覆盖项目硬约束             | 按分层记忆金字塔重新归类，标注冲突和适用范围     |
| 忽视压缩成本 | 为节省 token 删除关键上下文，导致重复排查或方向漂移        | 保留验证证据、当前改动范围、仍生效决策和阻塞项   |
| 旧记忆污染   | 已过期决策或历史错误结论继续影响当前任务                   | 标注过期原因，优先采用最新验证证据               |

异常边界：

1. 压缩后如果无法判断当前主线目标，必须暂停并生成阻塞清单。
2. 压缩后如果无法定位已改文件，必须先恢复改动范围，不得继续编辑。
3. 压缩后如果验证证据缺失，交付状态只能标为“未验证”或“部分完成”。
4. 压缩恢复时不得批量重读无关目录，只能按入口文件、目标文件、直接引用和错误证据逐步加载。

## 质量标准

- Session summary必须在会话结束时立即生成，不能拖延
- 决策记录必须包含"撤销条件"，避免过早固化
- 规范沉淀必须有正/反例，不能只有文字描述
- 记忆恢复时优先加载与当前任务最相关的内容
- 总记忆加载量控制在1000 tokens以内，超过时优先丢弃最旧的记录
- 项目规范冲突时，以时间最近的为准，并标注冲突
- 对话历史超过上下文预算 60% 时必须先生成结构化摘要，超过 80% 时必须停止加载非必要资料
- 结构化摘要必须包含用户目标、已确认决策、当前改动范围、未决问题/阻塞、验证证据/下一步
- 未命中用户指定、代码引用、错误证据或任务依赖时，不得预读全量 references 或无关模块
- 记忆写入必须区分 L1 对话级、L2 会话级、L3 项目级、L4 用户级，不得跨层污染
- 压缩后必须保留主线目标、改动范围、验证证据和未解决阻塞；缺失任一项时不得判定完成
- 跨轮对话必须继承主线目标、已确认决策、当前执行位置、阻塞状态和验证状态；用户只说“继续/下一步”时按上一轮下一步执行
- 记忆处理必须遵循 CRUL 生命周期：创建有来源，检索有触发，应用有边界，更新有撤销或过期条件
- 记忆默认静默应用；除非用户询问、依据存在争议或影响交付边界，不得主动暴露“根据记忆”的内部来源
- 敏感记忆必须上下文隔离，不得在无关任务中主动引用或写入普通项目规范
- 新增记忆必须先判定 `user / feedback / project / reference` 主类型，再映射到 L1-L4 分层
- 强制创建、选择性创建、禁止创建必须有明确触发条件；无法判断失效条件时不得写入长期记忆
- 记忆治理必须防止膨胀、冲突和透明度不足；影响交付边界的记忆依据必须可复核

## 失败回退机制

| 步骤                                             | 失败条件                                                            | 回退目标                                                            | 最大重试 | 不可恢复时升级路径                                   |
| ------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------- | -------- | ---------------------------------------------------- |
| 第一步：会话结束记录（Session Summary）          | 会话信息不完整或跨越多次中断                                        | 基于已有信息生成骨架summary，标注"信息可能不全"                     | 2        | 输出草稿，提示用户补充关键决策和遗留问题             |
| 第二步：决策记录（Decision Record）              | 决策选项信息不足，无法量化对比                                      | 记录已知选项 + 标注"待补充"字段                                     | 1        | 输出决策骨架，建议补充选项分析后回填                 |
| 第三步：规范沉淀（Convention Capture）           | 规范来源不清晰或正反例难以提炼                                      | 仅记录规范内容，标注"示例待补充"                                    | 2        | 输出规范文字描述，建议后续任务中补全正反例           |
| 第四步：新会话记忆恢复（Progressive Disclosure） | Layer加载超出token预算                                              | 优先丢弃Layer 3 References，保留Layer 1+2                           | 1        | 输出已加载记忆清单，提示用户手动选择关键References   |
| 记忆分层写入                                     | 临时信息、项目规范和用户偏好混写                                    | 按 L1-L4 重新归类，保留来源和适用范围                               | 1        | 标注"记忆层级待确认"，请求用户确认归档层级           |
| 上下文压缩恢复                                   | 压缩后丢失主线目标、改动范围、验证证据或阻塞项                      | 使用 Context Summary 五字段重新生成摘要                             | 2        | 标注"压缩恢复不完整"，停止扩大修改并输出阻塞清单     |
| 对话状态继承                                     | 无法判断“继续/下一步”对应的上一轮目标或下一步动作                   | 回读最近的 Context Summary，恢复主线目标、执行位置和验证状态        | 1        | 标注"对话状态不明"，请求用户确认继续哪条主线         |
| 记忆生命周期失衡                                 | 只创建不检索、只检索不更新、旧记忆与新证据冲突                      | 按 CRUL 重新标注 Create/Retrieve/Use/Learn 阶段，更新过期和撤销条件 | 1        | 标注"记忆生命周期待确认"，请求用户确认保留或废弃规则 |
| 敏感记忆污染                                     | 敏感信息被写入普通摘要、项目规范或无关交付说明                      | 立即隔离敏感内容，只保留任务必要风险描述                            | 0        | 停止扩散引用，请求用户确认删除或降级处理             |
| Typed Memory 归类错误                            | user、feedback、project、reference 混写，或即时反馈被升级为长期偏好 | 按类型映射表重新归类，并标注主类型、关联类型和适用范围              | 1        | 标注"记忆类型待确认"，请求用户确认归类               |
| 记忆创建策略误判                                 | 应强制创建的约束未记录，或禁止创建的信息被写入长期记忆              | 重新判定强制/选择性/禁止创建，补写撤销条件或删除污染项              | 1        | 标注"记忆创建策略待确认"，停止继续沉淀同类记忆       |
| 记忆膨胀                                         | 恢复任务时加载大量低价值历史、无关 reference 或过期细节             | 执行记忆瘦身，仅保留有效目标、决策、约束、验证方法和阻塞项          | 1        | 标注"记忆膨胀待治理"，请求用户确认保留清单           |
| 记忆冲突                                         | 同一项目存在互斥规范、路径、验证口径或用户偏好                      | 按时间、证据强度、风险等级和用户确认顺序裁决，旧规则标注过期        | 1        | 标注"记忆冲突待裁决"，请求用户确认有效规则           |
| 透明度不足                                       | 记忆影响交付边界、风险判断或默认假设，但未说明依据                  | 补充来源类别、适用范围和是否仍需确认                                | 1        | 标注"记忆依据待说明"，暂停依赖该记忆扩大修改         |

## 关联Skill

- **Spec驱动开发** — 将spec和design决策记录到项目记忆
- **软件项目总控** — 将通用项目边界、架构、发布和交付记录到项目记忆
- **网站项目总控** — 将站点配置、部署路径、交付材料和运维清单记录到项目记忆
- **任务拆解与执行** — 将task summary记录到项目记忆
- **技术选型** — 选型决策自动记录到项目记忆
- **代码生成** — 编码前加载项目规范，编码后记录新发现规范
