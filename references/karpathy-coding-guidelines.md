# Karpathy编码规范

基于Andrej Karpathy对LLM编码陷阱的观察，提供4条核心编码原则。

## 输入要求

1. **代码片段**（可选）：需要评估的代码
2. **具体问题**（可选）：如"这段代码是否过度设计"
3. **场景描述**（可选）：编码场景说明

## 执行流程

### 第一步：明确目标与假设

- 识别用户真实目标和成功标准
- 标注不确定信息，必要时向用户澄清
- 列出关键假设，不把猜测隐藏在代码里

### 第二步：应用四大原则

- 用“编码前思考”检查需求歧义
- 用“简洁优先”排除过度设计
- 用“精准修改”限制变更范围
- 用“目标驱动执行”定义验证闭环

### 第三步：检查代码或方案

- 对照四大原则逐项检查
- 识别具体代码位置、改动点或设计风险
- 区分必须修复和可选优化

### 第四步：输出改进建议

- 给出最小修改方案
- 提供修改前后对比或明确执行步骤
- 标注保留现状的理由和风险

### 第五步：验证与沉淀

- 验证建议是否满足原始目标
- 将可复用的编码规范、陷阱和决策记录到项目记忆

## 四大原则

### 原则1：编码前思考（Think Before Coding）

**不要假设。不要隐藏困惑。暴露权衡。**

编码前必须：

- 明确陈述假设——如果不确定，提问而不是猜测
- 存在多种理解时，列出选项——不要默默选择
- 存在更简单方案时，说出来——该推回时推回
- 遇到不清楚的地方，停下来——说出困惑所在，提问

**反模式**：

- 用户说"导出用户数据"，直接写导出所有用户的代码（假设了范围、格式、字段）
- 用户说"让搜索更快"，直接加缓存和索引（假设了"更快"的含义）

**正确做法**：

```
导出用户数据前，我需要澄清：
1. 范围：导出全部用户还是筛选后的子集？
2. 格式：JSON/CSV/直接API返回？
3. 字段：哪些字段？（有些可能涉及隐私）
```

### 原则2：简洁优先（Simplicity First）

**最少代码解决问题。不要 speculative。**

- 不要超出需求的功能
- 不要为单次使用代码做抽象
- 不要未被要求的"灵活性"或"可配置性"
- 不要为不可能场景做错误处理
- 写了200行但50行能搞定，重写

**自检问题**："资深工程师会说这过度复杂吗？"如果是，简化。

**反模式**：

- 用户说"计算折扣"，生成Strategy模式+抽象类+配置对象（30行设置做简单计算）
- 用户说"保存用户偏好"，加缓存、验证、合并、通知（没人要求的功能）

**正确做法**：

```python
# 简单直接
def calculate_discount(amount: float, percent: float) -> float:
    return amount * (percent / 100)
```

### 原则3：精准修改（Surgical Changes）

**只碰必须碰的。只清理自己制造的。**

编辑现有代码时：

- 不要"改进"相邻代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格，即使你自己会不同做法
- 发现无关死代码，提一下——但不要删

你的修改制造孤儿时：

- 删除**你的修改**导致的未使用import/变量/函数
- 不要删除预先存在的死代码，除非被要求

**测试标准**：每一行修改都能追溯到用户的请求。

**反模式**：

- 修复空邮箱Bug时，顺便"改进"邮箱验证、加用户名验证、改注释、加docstring
- 添加上传日志时，改引号风格、加类型提示、重排空白

**正确做法**：

```diff
-     if not user_data.get('email'):
+     email = user_data.get('email', '')
+     if not email or not email.strip():
          raise ValueError("Email required")
```

### 原则4：目标驱动执行（Goal-Driven Execution）

**定义成功标准。循环直到验证。**

把指令式任务转化为可验证目标：

- "加验证" → "写无效输入的测试，然后让它们通过"
- "修Bug" → "写复现Bug的测试，然后让它通过"
- "重构X" → "确保重构前后测试都通过"

多步骤任务时，陈述简要计划：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

强成功标准让你独立循环。弱标准（"让它工作"）需要持续澄清。

## 失败回退机制

| 失败场景 | 回退目标 | 最大重试 |
|----------|----------|----------|
| 目标模糊（"让它工作"类） | 拆分为可验证子项，附验证方法 | 2 |
| 歧义无法澄清 | 列2-3种最可能理解，标注"假设" | 2 |
| 需求边界模糊 | 保守保留核心功能，标注"待确认" | 1 |
| 测试环境/依赖不可用 | 最小化方式验证核心逻辑（直接调用+断言） | 2 |
| 验证失败（外部依赖问题） | 标注"外部依赖异常"，记录复现条件 | 1 |
| 连续3轮未通过验证 | 暂停循环，产出当前最佳版本+差异报告 | 0 |

不可恢复时输出阻塞清单和升级路径，由用户决策。

## 反 AI 糟粕代码门禁

生成或审查代码时，以下模式必须作为质量门禁逐项排查：

| 门禁项 | 典型表现 | 处理规则 |
| -------------- | ------------------------------------------------------ | ---------------------------------------------------------- |
| 过度抽象 | 为一次性逻辑创建策略模式、工厂、管理器、配置层 | 删除抽象，回到直接、可读、可测的实现 |
| 废注释 | 注释重复代码含义、为显而易见的赋值写解释 | 删除废注释，仅保留解释业务约束、边界条件、危险操作的注释 |
| 模板化错误处理 | 每个函数机械包 `try/catch`，catch 内吞异常或只返回空值 | 让异常在合适层级处理；catch 必须记录、转换或给用户可见反馈 |
| 防御式臆想 | 为未出现的输入、未要求的插件点、未知未来需求堆分支 | 删除未被需求或测试证明的分支 |
| 全文件重写 | 为小修复重排格式、重命名无关变量、搬动无关函数 | 回退到局部修改，只触碰完成目标所需代码 |
| 不可验证产物 | 只给代码，不给 lint/test/build/curl/手动验收路径 | 补齐最小验证命令或说明无法验证的具体阻塞 |

交付前必须回答：

1. 新增代码是否直接服务于用户目标？
2. 是否存在可删除而不影响功能的抽象、注释或配置？
3. 是否触碰了与任务无关的文件、函数或格式？
4. 是否有明确验证证据支撑"已完成"？

## 依赖管理锁定

新增、升级或锁定依赖时，必须遵守以下规则，避免构建漂移和环境差异。

### 强制规则

| 规则 | 说明 | 反例 |
|------|------|------|
| 版本锁定 | 所有依赖必须使用锁文件精确锁定版本 | `composer.json` 写 `"laravel/framework": "^10.0"` 但未提交 `composer.lock` |
| 禁止浮动版本 | 业务代码禁止使用 `latest` / `*` / `dev-main` / `@stable` 等浮动约束 | `"vue": "latest"` |
| 锁文件入库 | `composer.lock` / `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` 必须提交到代码库 | `.gitignore` 排除锁文件 |
| 子依赖锁定 | 不依赖平台自动解析子依赖版本，以锁文件全量快照为准 | 仅锁顶层依赖，子依赖由 registry 解析 |
| 新增依赖必审 | 新增依赖必须说明用途、替代方案和体积影响，禁止为单次任务引入重框架 | 为计算折扣引入整个 `symfony/expression-language` |
| 升级必分批 | 升级依赖必须分 minor → major 升级，每级跑测试；禁止跨大版本一步升级 | 直接从 PHP 7.4 跳到 8.3 不验证 |
| 漏洞依赖处置 | 发现 CVE 必须在 7 天内升级或替换，未升级前标注为已知风险 | 已知漏洞依赖长期留存 |

### 检查清单

交付前逐项确认：

- [ ] 锁文件存在且与 `composer.json` / `package.json` 一致
- [ ] 业务代码无 `latest` / `*` / `dev-*` 浮动约束
- [ ] 新增依赖已说明用途和替代方案
- [ ] 升级路径经过分阶段测试
- [ ] 已知漏洞依赖已标注或已处置

### 失败回退

| 失败场景 | 回退动作 |
|----------|----------|
| 锁文件与配置不一致 | 用 `composer install` / `npm ci` 重新生成锁文件后提交 |
| 升级后测试失败 | 回退到上一稳定锁文件，分文件分模块排查 |
| 新增依赖体积过大 | 评估轻量替代方案，必要时拒绝引入 |

## 质量标准

- 评估必须基于代码实际内容，不能泛泛而谈
- 每个原则的评估必须有具体的代码位置引用
- 改进建议必须提供具体的修改前后对比
- 不得为符合规范的代码强行找问题
- 评估应平衡：不是追求绝对完美，而是避免常见陷阱
- 必须逐项检查「反 AI 糟粕代码门禁」，发现命中项时优先压缩或删除
- 不能用新增抽象、泛化配置或模板化错误处理替代真正的业务理解

## 关联Skill

- **code-review**（代码审查）— 用 `code-review` 进行全面的技术审查（Bug/安全/性能）
- **code-generation**（代码生成）— 用 `code-generation` 生成功能代码，再用本Skill评估是否符合规范
- **refactoring**（重构建议）— 用 `refactoring` 获取结构优化方案，再用本Skill检查是否过度设计
- **project-memory-management**（项目记忆管理）— 记录可复用的编码规范、陷阱和决策清单
